# Yudao DataHub 后端仓库约束

## 适用范围与事实来源

- 本仓库是 `yudao-cloud` 后端。开始工作前先查看 `git status`，保留用户已有改动，不覆盖、不回退无关文件。
- 修改 `yudao-framework`、`sql/postgresql` 或具有本地 `AGENTS.md` 的业务模块前，必须继续读取目标目录最近的 `AGENTS.md`；根规则与局部规则同时生效，局部规则只细化对应范围。
- 版本化 Skill 的唯一源是 `.agents/skills/yudao-datahub-development`；个人全局安装只是派生副本。维护 Skill 时先修改并校验仓库版本，再同步安装副本，避免两套规则漂移。即使 Skill 未安装，本文件和局部 `AGENTS.md` 仍独立生效。
- 活动模块、Java/Spring/Maven 版本和构建配置以当前 `pom.xml`、源码和测试为准；README 与旧样例仅作次级参考。
- 新的业务能力应归入现有业务模块；可复用技术能力按“组件优先与能力归属”处理。不得因旧名称或旧文档重新创建已经拆除、停用的模块。

## 单租户产品约束

- 数据中台业务（asset、dataforge、governance、modeling、supply 及 `dh_*` 表）采用单租户，不保留业务租户列、租户上下文、租户过滤或逐租户执行，不引入固定租户编号兼容层。
- 保留 system、infra、bpm 和 framework 脚手架的通用租户能力及关闭开关；外部产品的执行租户（如 DolphinScheduler tenantCode）按外部协议处理。
- 单租户不取消登录、接口权限、部门数据范围、对象授权、应用签名与审计。平台尚未上线，删除的业务租户协议无需兼容，但数据库变更仍提交编号迁移并同步新库基线。

## 模块与代码结构

- 业务模块遵循 `yudao-module-<module>/{api,server}`。跨模块仅依赖对方 `*-api`；不得直接依赖或导入对方的 Controller、Service、Mapper、DO 或 `*-server`。
- 管理端接口沿用 `controller/admin/<business>/vo`、`service/<business>`、`dal/dataobject/<business>`、`dal/mysql/<business>` 分层。
- Controller 使用 `@Tag`、`@Operation`、统一校验、细粒度权限和 `CommonResult` 契约，不向外暴露 DO，也不要手写 `/admin-api` 前缀。
- DataHub 业务 DO 继承 `BaseDO`，不声明 `tenantId` 或继承 `TenantBaseDO`；脚手架实体按自身契约维护。Mapper 优先复用 `BaseMapperX` 与 `LambdaQueryWrapperX`。
- 简单同形转换优先使用框架 `BeanUtils`；复杂 JSON、嵌套对象、计算或富化字段使用显式 converter，并测试转换边界。
- 输入格式校验放 ReqVO；存在性、唯一性、状态、引用、权限与并发不变量放 Service。预期业务失败使用模块 `ErrorCodeConstants`。新增错误码前先在 `ServiceErrorCodeRange` 确认模块区间，并运行全仓库错误码检查；数值、artifact、Java package 与领域 owner 必须一致。
- 多表写入、状态迁移、锁或并发不变量使用 `@Transactional(rollbackFor = Exception.class)`；不要给所有简单 CRUD 机械加事务。使用锁时确认方法经过 Spring 代理并处于真实事务内，检查自调用、非 `public` 方法和异步线程导致的事务失效；不要在持锁事务中执行不受控的 Feign、BPM、文件或 MQ 调用。

## 组件优先与能力归属

- 新增技术能力前，先检索根 `pom.xml` 中当前启用的 `yudao-framework` starter、相关业务模块的 `*-api`、现有调用方和测试。重点排查已有的 `*Util`、`*Helper`、`*Manager`、`*Executor`、`*Factory`、解析器、转换器、方言、模板和集成客户端；不得只因不知道入口就在业务模块重复实现。
- 业务模块负责领域规则与流程编排；可跨业务复用的技术机制应由职责相符的 framework 组件承载。framework 组件不得依赖 `yudao-module-*`，其公共 API、配置和模型不得包含业务 VO、DO、审批状态、权限码或模块专属枚举。
- 优先通过组件公开 API、扩展点或 SPI 复用能力，不复制组件内部实现，也不创建实质上重写组件逻辑的包装类。对已有组件能力，或经评估确认应下沉组件的能力，业务侧只保留薄适配层，用于领域模型映射、数据源解析、配置组装、错误语义转换和业务流程编排；底层技术执行委托组件。
- 当现有组件缺少能力时，先判断该能力是否属于组件职责、是否与具体业务解耦、是否可能被多个模块或数据库产品复用。若属于组件能力，应先在组件中补齐稳定接口或扩展点、实现和测试，再由当前业务模块调用；不得先在业务模块落一个通用实现并长期复制。若只是当前领域的一次性规则或尚不能形成稳定抽象，则留在业务模块，避免把业务策略塞入 framework。
- 扩展组件时必须评估向后兼容、自动配置与开关、线程安全、事务/连接边界、租户与安全上下文、异常契约、日志指标以及依赖体积；至少验证组件自身和当前直接调用方。不要为尚无真实用例的假想通用性提前扩展。
- 设计或评审新增通用技术类时，必须给出“检索过哪些组件、为何可直接复用/需要扩展/应留在业务”的结论。发现现有组件接口不安全或不足时，不得静默绕过；应记录缺口，并在职责成立时优先修复组件。
- 缓存优先复用 Redis starter，按业务对象及必要的用户/应用范围设计 key，不加入业务租户维度；HTTP 短时防重优先评估 protection `@Idempotent`，临界区互斥优先评估 Lock4j，但二者都不能代替数据库唯一约束、乐观锁/CAS、行锁或持久业务幂等记录。缓存失效和通知应与事务成功提交对齐。

### 数据库能力归属

- 数据库元数据读取、产品/方言识别、标识符处理、通用类型映射、建表 DDL、已支持语义内的 SQL 生成/模板执行、数据库操作器、批量写入及运行时全量/增量搬数，优先复用 `yudao-spring-boot-starter-biz-dbswitch` 的公开能力。新增数据库产品或通用数据库能力时，优先通过 DB Switch 的工厂、接口或 SPI 扩展，并补充对应方言与真实数据库测试。
- 当前 DB Switch 能力不能满足需求时，先区分“通用数据库机制”和“业务规则”。统一方言能力、类型转换、DDL 计划/差异、脚本解析执行、安全模板渲染、能力探测等适合评估后下沉 DB Switch；建模审批与版本状态、部门/对象授权、业务数据源记录、任务调度、菜单字典和领域初始化数据继续留在所属业务模块。
- 不把“存在枚举或接口”当作能力已完备的证据。采用前检查实际实现、驱动、调用方和测试；对有限或实验性路径先验证再使用，避免业务代码依赖未经证明的兼容性。
- DB Switch 支持必须按“数据库产品 × 元数据/DDL/read/write/sync 操作”逐项证明，不能从某个枚举、接口或单一调用方推断整种数据库完整受支持。
- DB Switch 的运行时数据迁移不等于项目数据库的版本化升级。任何由本仓库发布、管理的平台数据库结构或数据变更仍必须提交下面规定的 `sql/postgresql/migrations/NNNN_*.sql`，不得用运行时同步、自动建表或全量基线替代编号迁移。

## 服务、安全与数据范围

- 跨模块/服务契约由提供方定义在 `*-api`，实现放在 `*-server`；消费方只依赖 API artifact，并按现有 `ApiConstants`、Feign 注册和 `CommonResult` 契约调用。前端不得访问 `/rpc-api/**`。
- 跨服务读写只能通过提供方 `*-api` 或正式消息契约，不直接修改其他服务业务表。根据是否需要即时结果、可用性与一致性选择同步 RPC 或异步消息；同步写必须定义超时、重试、幂等键、未知结果与补偿/对账，异步写必须定义可靠投递、重复/乱序处理和失败处置。本地 `@Transactional` 不覆盖 Feign、MQ、BPM、文件服务或其他服务数据库。
- 单租户不等于取消部门/对象数据权限。每个新增的列表、详情、导出及写操作都必须明确：平台内全可见、部门范围、对象级 Guard，或业务权限 RPC。
- 不信任客户端传入的 `tenantId` 或 `orgId` 作为授权依据。前端隐藏按钮不能代替后端权限与数据范围校验。
- 外部入口必须剥离 `login-user`、租户、数据权限开关等内部身份/控制头；服务只能在经过服务身份认证的 RPC 通道上信任这些头。`/rpc-api/**` 的 `permitAll` 必须同时具有不对外路由、网络隔离或签名/mTLS 等可验证门禁，并测试伪造头、直连服务、网关清洗和合法 Feign 传播。
- 面向外部调用的开放 API 必须把防重放与领域幂等分开设计：nonce 使用跨节点原子且带 TTL 的存储并按应用隔离；签名覆盖 method、规范化 path/query、body hash、timestamp、nonce 和版本，同时定义时钟窗口、密钥轮换与常量时间比较。
- 密码、令牌、真实账号、明文连接串不得进入源码、SQL、测试数据、日志或版本控制配置。

## API 传输与运行时集成

- Java 类型不等于 JSON 类型。当前全局序列化器会把 JavaScript 安全范围内的 `Long` 输出为数字、超出范围的输出为十进制字符串；默认 `LocalDateTime` 输出毫秒时间戳，字段存在 `@JsonFormat` 时才按其格式输出。修改接口或生成代码时必须按真实 VO/注解同步前端契约，禁止诱导前端对 ID 做有损数字转换。
- 对金额、比例、度量等必须精确的小数，不能仅把前端 TypeScript 改成 `string`；后端线协议必须在 JSON 解析前输出十进制字符串，前端 API、表单、表格、计算和提交全程保持字符串或使用项目明确采用的十进制实现，禁止经过 `parseFloat`、普通原生算术等有损路径。近似展示数值可按明确契约使用 JSON number。
- 导入导出复用现有 Excel 工具及 `@ApiAccessLog` 约定，并应用与列表/详情一致的数据范围。审批、发布、越权覆盖、权限变更和破坏性操作按审计需要评估业务操作日志，不给全部 CRUD 机械加日志注解。
- 业务级、分布式、可运维任务优先复用现有 XXL-Job 组件。数据中台任务按单平台扫描和处理，不使用 `@TenantJob`、`@TenantIgnore` 或租户参数；明确执行人、对象权限与分批抢占边界。处理器保持薄、可重试且业务幂等，资源重型任务不得默认依赖 `parallelStream` 或无显式 executor 的 common pool。`@Scheduled` 仅用于明确的内部维护/心跳，并说明集群多实例语义。
- MQ/事件消费者按至少一次投递设计幂等，处理重复、延迟和乱序；Spring `ApplicationEvent` 不是持久化跨服务消息。不得假设仓库已有统一 outbox/inbox，必须先检索并验证；没有合适实现时由领域建立可靠投递、lease/崩溃恢复、最大重试、死信/人工处置、对账和清理机制。HTTP `@Idempotent` 也不能替代任务、回调或消费者的领域幂等。
- 文件存储优先复用 infra `FileApi`，但当前 `byte[]` 契约只适合有明确大小上限的文件；大文件应使用经验证的流式或预签名能力。对象存储上传与平台元数据登记是两阶段结果，必须等待并处理登记失败、重试/补偿和孤儿对象清理。业务模块不得依赖 `infra-server` 或直接绑定对象存储 SDK；WebSocket 复用 starter 的认证会话和发送能力，通知不能代替持久业务状态。
- 审批与流程能力复用 `bpm-api`，BPM 之外的模块不得直接依赖 `bpm-server`、Flowable Service 或流程引擎表。业务模块拥有领域状态机；跨进程事件与本地 `ApplicationEvent` 分离，事件信封至少包含稳定 `eventId`、schema/version、occurredAt、aggregate/process correlation 和可排序 revision。启动、回调、取消和对账必须处理跨服务非原子性以及重复、超时、乱序事件。
- `@ApiAccessLog` 只表示访问日志，不等于领域审计。审批、发布、授权、强制覆盖等重要操作应在成功提交后记录 actor、object、前后状态/摘要、原因、结果和 correlation/trace，并对敏感字段脱敏。

## PostgreSQL 变更与有序迁移

- 任何新增或修改由本仓库发布、管理的平台 PostgreSQL 表、列、约束、索引、序列、字典、菜单权限、初始化数据或数据修复的任务，都必须在 `sql/postgresql/migrations` 新建一个可独立执行的增量 SQL 文件；只修改 Java/现有基线而不提供增量脚本不算完成。
- 运行时根据用户任务对外部或目标数据源生成、执行的动态 DDL 走 DB Switch，不因该动态 DDL 本身创建平台仓库迁移。若该功能同时修改平台自身的任务表、字典、菜单或其他持久状态，平台部分仍必须提交编号迁移。
- 新增迁移文件统一使用全局四位十进制前缀：`NNNN_<module>_<short-description>.sql`，例如 `0001_governance_standard-table.sql`、`0002_governance_standard-data.sql`、`0010_system_menu-permission.sql`。四位补零用于保证文件名排序就是执行顺序。
- 创建文件前扫描 `sql/postgresql/migrations` 下文件名开头匹配 `^[0-9]{4}_` 的文件，取最大编号加一；目录或编号文件不存在时从 `0001` 开始。一个任务有多个存在依赖的脚本时使用连续编号，并按“结构 → 必要数据/字典 → 菜单/权限 → 数据修复”的真实依赖排序。
- 编号在整个 `sql/postgresql/migrations` 目录内全局唯一，不按模块重新从 `0001` 开始。合并或交付前必须重新扫描，发现并行分支编号冲突时调整为新的最大编号加一，并同步脚本头中的依赖说明。
- `sql/postgresql` 根目录中的历史未编号脚本保持原名、原路径，不批量移动或重命名；它们不自动纳入新的编号序列。若新迁移依赖某个历史脚本，必须在文件头和交付说明中明确写出该前置脚本。
- 已合并、已发布或可能已执行的迁移文件视为不可变。后续修正必须创建下一个编号文件；只有尚未交付且属于当前任务的新文件才能原地修改。
- `datahub-center.sql` 是新库全量基线。最终结构发生变化时应同步更新基线，并在文件开头声明唯一的 `-- Included migrations through: NNNN`，其编号必须等于当前最高迁移；已有数据库只能执行新增的编号迁移，不得用全量基线代替升级脚本。
- 每个编号 SQL 文件头至少写明：编号、用途、前置脚本或前置状态、是否可重复执行、不可逆操作与回滚说明。优先使用 PostgreSQL 可重放、加法式写法；破坏性 DDL、长锁表操作或不可逆数据更新必须显式说明风险。
- 一个迁移应包含完成该增量所需的全部 SQL，不得只写伪代码、遗漏菜单权限或依赖人工补语句。事务边界应按 PostgreSQL 操作能力明确设计。
- 代码生成器输出的未编号 `sql/sql.sql` 只可作为候选输入，不得直接作为迁移交付或执行。应把完整且经复核的结构、字典、菜单与权限增量整理进新的全局编号迁移；生成结构和菜单分文件时按依赖使用连续编号。
- SQL 交付时必须在最终说明中单列“SQL 执行顺序”，按编号列出精确文件路径、适用对象（新库/已有库）及任何前置条件；即使只有一个文件也要列出。

## 验证与交付

- 后端验证从受影响的 Maven 模块开始，再按风险扩大；指定单测跨 reactor 运行时使用 `-Dsurefire.failIfNoSpecifiedTests=false`。
- 修改根 POM、BOM 或共享组件时，检查 effective POM、Spring Boot/BOM/注解处理器版本对齐、依赖收敛、Jakarta/Spring 兼容以及 Jackson 2/3 边界；至少运行最小应用上下文和 JSON 契约测试，不能只用编译成功证明运行兼容。
- 提交前运行 `python tools/quality/run_all.py`。质量脚本是确定性门禁，不能以人工阅读或 Skill 判断替代；若环境无法运行，最终说明必须明确列出未验证项。
- 修改 framework 组件时，先验证组件模块，再验证所有本次受影响的直接消费模块；涉及 DB Switch 方言、DDL、元数据或搬数时增加方言输出测试，并对关键行为使用真实目标数据库/Testcontainers 验证。
- PostgreSQL 方言、JSONB、锁、部分索引、迁移重放等行为使用真实 PostgreSQL/Testcontainers 验证，不能以 H2 结果替代。
- 修改代码生成模板时运行对应生成器专测。代码生成结果只是起点，仍须复核输出路径、DO/VO 分层、Long/精确小数/时间传输类型、请求响应差异、返回泛型、权限、数据范围、事务、约束、错误码和测试。
- Testcontainers 用例若因无 Docker 等条件被跳过，即使 Maven 退出码为 0 也不能表述为通过；必须核对 Surefire 的执行/跳过数量。
- 最终说明必须列出执行过的检查、结果、未执行检查及原因；不得把未运行或因环境跳过的测试表述为通过。
