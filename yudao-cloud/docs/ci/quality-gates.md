# DataHub 质量门禁

本项目把长期约束拆成两层：`AGENTS.md`/Skill 负责开发时决策，仓库脚本与 CI 负责可确定验证。CI 只认可脚本退出码，不把模型判断或人工勾选当作自动门禁。

## 后端

- 本地统一入口：`python tools/quality/run_all.py`
- 门禁自测：`python tools/quality/run_all.py --self-test`
- PR 与主分支工作流：`.workflow/backend-quality.yml`
- 当前检查：PostgreSQL 迁移编号、头信息、依赖、基线标记和不可变性；全局错误码重复/格式/已确认区间；业务模块与 Framework 依赖边界。
- CI 使用后端真实主分支 `origin/master-jdk25` 区分历史债务和本次新增问题。`--strict` 仅用于专门清理历史债务，不应把无关历史问题塞进普通功能 PR。

## Gitee 启用步骤

版本库中的 `.workflow/*.yml` 是流水线定义，但“文件已提交”不等于“分支保护已经生效”。仓库管理员仍需在 Gitee 中完成一次性配置：

1. 启用 Gitee Go，并确认仓库识别对应的 backend/frontend workflow。
2. 给流水线执行身份授予只读代码权限；门禁不得保存数据库密码、令牌或真实连接串。
3. 保持目标分支与各仓库实际主分支一致：后端当前为 `master-jdk25`，前端当前为 `master`；以后更名时必须同步修改对应 workflow。
4. 在合并保护中把对应质量流水线设为必需成功检查，禁止管理员日常绕过。
5. 首次运行核对 Python、Node 与 pnpm 版本以及执行日志；未实际运行、被跳过或因平台配置没有触发，都不能表述为门禁通过。

如果团队使用其他 CI 平台，复用上面的统一命令即可；不要在另一份 YAML 中重新实现规则，从而形成两套不一致的判断逻辑。
