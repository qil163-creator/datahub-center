# 模型管理统一设计落地方案

适用项目：yudao-cloud 与 yudao-ui-admin-vben。设计日期：2026 年 10 月 10 日。

模型管理定位为“设计数据表，管理发布和变更”。用户围绕维度表、明细表、汇总表和应用表工作，列表、字段表单和 ER 画布使用同一份模型定义。模型管理定义结构、粒度、业务口径与关联关系；数据研发通过 SQL、程序和 ETL 产生数据。发布结构不会自动完成数据加工。

当前精简版本为 0131：保留统一设计、ER、发布变更及业务分类；退役概念建模、旧主题规划、多环境和后台巡检，实库基线合并到部署记录。最终 11 张业务表及 7 张迁移证据表。以[当前迁移执行与验证说明](modeling-unified-migration-runbook.md)为准，已有库执行一份 0131 完整脚本；下文 0123—0126 的迁移分工、历史表名和阶段说明仅用于追溯。平台 SQL 不连接用户的数据源，不修改外部目标表。

## 产品范围

默认入口保留“模型管理”和“发布记录”，数仓分层、数据域、业务分类等沿用架构规划配置。模型管理包含列表和 ER 两种浏览方式，打开任何模型都进入同一个编辑器。

| 能力 | 本轮改造目标 | 边界 |
| --- | --- | --- |
| 模型列表 | 按表类型、数据域、分层、名称查找；创建、从已有表导入 | 分页与授权过滤由后端完成，不在浏览器拼接逻辑和物理两张分页表 |
| 统一编辑器 | 基本信息、字段、类型专属配置、关系、目标配置 | 字段表单与 ER 抽屉共用编辑和保存逻辑 |
| ER 画布 | 模型和字段关系、基数、布局；双击编辑同一模型 | 业务关系默认不生成数据库外键，不混入加工血缘 |
| 发布 | 检查、固定设计版本、预览目标结构差异与 SQL、执行部署 | 固定版本与外部 DDL 分阶段完成，分别记录结果 |
| 变更 | 草稿与设计版本对比、设计与目标结构对比、任务与服务影响 | 无证据的影响显示“未知”，不能显示为“无影响” |
| 使用情况 | 关联开发任务、质量结果、实际血缘与服务引用 | 调用所属模块 API，不复制任务设计器或质量执行器 |
| 业务分类 | 保留独立分类树及管理页面、接口、菜单权限和表数据 | 不重新引入已退役的业务过程或概念模型关联 |

首期沿用当前单目标使用习惯：一个模型默认展示一个部署目标；历史上一对多的目标绑定分别保留，不自动合并或删除。新增多目标批量部署、跨引擎一键适配、完整指标中心不属于第一期必交能力。

## 工作台功能退役（0126）

删除建模专属协作策略、审批流程、归档检查报告、收件箱、业务对象变更分发与引用变更回执，包含后端控制器、服务、任务、BPM 依赖、按钮权限及业务表。访问范围明确改为“角色权限 + 租户隔离”：租户内具备相应查询/写入权限的用户可以访问模型，不再执行旧对象所有者或部门协作 ACL。此范围变化为产品决策，不能描述为原 ACL 无变化。

即时设计检查、字段标准门禁、部署/检测记录和治理登记继续保留。检查返回结果直接供编辑器使用，不再生成可查询的归档报告。概念模型可作为高级业务说明编辑；概念生成仅调用统一创建服务初始化新设计；旧概念 `sync-apply` 入口与直接改写逻辑字段的方法删除，历史预览与记录继续只读。

后续 `0127` 完整移除业务过程、业务对象及其外部引用管理，不作为模型创建或发布的前置。模型直接维护数据域、可选主题域和数仓分层；概念实体直接维护名称、属性与关系。明细表的粒度和业务时间校验保留，业务域分类也保留。执行顺序及历史快照兼容说明见[功能移除说明](remove-business-process-object.md)。

0126 将退役七表的完整原行及相关菜单/授权变更原行保存在 `dh_modeling_workspace_removal_archive`，不提供业务 API，不参与授权。原 `dh_modeling_unification_map`、所有历史版本/部署记录和首次 ACL 备份保留；旧审查函数完成阶段使命后移除，不能通过删除旧 ACL 证据掩盖范围变化。

数据库管理的“引用影响”和“数据源引用控制”功能已退役，专用盘点 API、变更屏障及完成回执代码一并删除。0145 清理其专用表和菜单权限；数据源停用、删除不再执行该跨模块引用核验。

## 页面和操作流程

模型列表左侧按数据域组织，可切换分层视角。表类型使用页签或筛选，不把业务分类、数据域、主题、分层全部叠成必经目录。进入某目录后新建模型自动带入归属。已有规划对象继续复用，不为界面简化另建一套分类表。

列表显示中文名和表名、表类型、分层、当前设计版本、目标表状态、负责人、最近修改时间。设计状态与数据库状态分别显示，例如“存在草稿；数据库仍为 v3”，避免一个“启用”开关混合表达多个事实。

统一详情分为三个工作区：设计、发布与变更、使用情况。设计区包含字段表格、类型专属配置和关系；发布区包含目标配置、版本比较、DDL 与执行记录；使用情况展示关联任务和真实运行结果。高级配置默认折叠。

| 表类型 | 基础设计信息 | 按需展开 |
| --- | --- | --- |
| 维度表 DIMENSION | 实体含义、业务键、描述属性、历史策略 | 保留历史时才配置生效失效时间与当前记录标识；未知维度处理 |
| 明细表 DETAIL | 一行代表什么、组成粒度的字段、业务时间、关联维度 | 去重、快照组织方式、迟到与更正策略 |
| 汇总表 SUMMARY | 来源模型、分组维度、时间范围与归属、指标口径 | 过滤、重算方式、失效分组处理 |
| 应用表 APPLICATION | 消费场景、输出粒度、对外字段与刷新要求 | 兼容约定及消费方列表 |
| 贴源表 SOURCE | 来源、承接方式、来源业务键 | CDC 顺序、删除处理及保留约定 |

表类型与分层有关但不等价。类型用于确定必要设计项，分层用于组织与默认命名；选择类型可带入分层默认值，允许项目规则范围内调整。标准关联在字段级按需选择，不要求所有字段先挂标准才可保存草稿。

基本信息提供可选的“一行代表什么”入口，保存为模型头 `grain`；明细表或应用表已在专属配置填写粒度说明时可留空，不额外增加一项重复必填。明细表的粒度字段、业务时间等类型校验继续生效。`grain` 随统一保存、发布快照和治理标准检查传递，已同时纳入请求摘要与目标摘要；仅修改粒度也会改变对应摘要，不能复用修改前的标准门禁凭证。

日常操作依次为：新建或导入、编辑并保存草稿、发布检查、固定设计版本、确认部署计划、执行和核验、关联研发任务。每一步返回可追溯的对象和结果，重新打开页面后可以继续尚未完成的阶段。

## 一套定义与三种视图

统一身份使用 `modelId`，其数据库身份继续是原逻辑模型 ID。编辑上下文使用 `modelId + versionId + expectedRevision`。所有 ID 按无损字符串或当前 `string | number` 线协议传输，禁止在浏览器通过 `Number` 转换。

列表、表单和 ER 从统一查询接口获取定义。ER 节点只是当前模型及字段的展示投影，不能存另一份字段定义。表单与 ER 共用草稿保存入口；布局位置单独保存，不因拖动画布而产生新的设计发布版本。

关系引用使用模型 ID 与稳定 `fieldUid`。`field_pairs` 保存有序字段对，支持复合键；原 `source_field/target_field` 保留为遗留名称和显示回退。修改字段名称不更换 UID。删除被关系或指标配置引用的字段，必须在同一事务中处理引用或阻止保存，不能静默删除连线。

关系保存验证双方模型处于同一租户，操作者具备对应角色操作权限，字段属于对应编辑版本。关系变更与关联模型修订号更新使用真实事务；并发写按稳定 ID 顺序锁定或使用 CAS，避免后保存覆盖先保存。已发布版本的关系由 `relation_snapshot` 固定，历史为空表示未记录，不能从当前关系反推过去状态。

模型关系回答“怎样关联”，研发血缘回答“怎样加工出来”。模型部署到目标表的历史登记属于部署来源证据，不能冒充明细聚合为汇总的加工血缘。关联关系默认是平台虚拟关系；生成数据库外键作为独立的目标引擎能力按需启用。

## 数据结构与权威来源

保留现有表名与编号可以减少历史契约迁移。`logic` 和 `physical` 在存储层的旧名称不再决定前台菜单，也不代表仍有两套可编辑业务定义。

| 表 | 目标职责 | 处理方式 |
| --- | --- | --- |
| `dh_modeling_logic_model` | 唯一模型设计主表，名称、编码、归属、类型及修订号 | 原 ID 保留，增加定义 revision 与独立 layout_revision |
| `dh_modeling_logic_model_version` | 唯一设计字段、类型配置、业务快照与发布版本 | 原历史不改，增加 relation_snapshot；新发布固定完整关系 |
| `dh_modeling_logic_relation` | 当前 ER 业务关系 | 原关系 ID 保留，增加字段对与修订号 |
| `dh_modeling_physical_model` | 目标绑定，目标连接、实际表名、引擎配置和部署状态 | 原物理 ID 保留；清理阶段删除重复可变业务头字段 |
| `dh_modeling_physical_model_version` | 目标类型映射与发布产物，以及不可改写的旧物理历史 | 增加 design_version_id 和来源分类；新记录精确引用设计版本 |
| `dh_modeling_deploy_record` | 外部执行意图、结果、幂等、租约、核验与治理登记 | 原样保留物理 ID、物理版本 ID 与冻结载荷 |
| `dh_modeling_schema_baseline`、检测表 | 实库结构及检查证据 | 原样保留目标身份，不替换成统一设计 ID |
| `dh_modeling_unification_map` | 旧物理到唯一设计的映射、原始数据备份、差异审查证据 | 新增迁移账本，不作为第三份业务模型 |
| `dh_modeling_unification_state` | 准备与结构清理完成标志 | 新增迁移状态，不代替应用部署验证 |
| `dh_modeling_unified_menu_backup` | 菜单切换的完整前后镜像 | 新增迁移证据，不复制角色授权 |
| 概念模型及同步表 | 历史概念说明、来源、同步决策证据 | 不删除、不自动完成未决同步 |
| `dh_modeling_workspace_removal_archive` | 被删除协作、审批、报告、收件箱、分发、回执行的完整原始证据 | 0126 归档后删除七表；归档不参与业务授权且无 API |

设计版本和部署产物可以都包含字段快照：前者是业务定义的权威来源，后者固定目标类型与执行所需内容。目标快照不可独立编辑业务字段；服务必须从指定设计版本读取字段并经 DB Switch 派生目标结构，不接受客户端任意提交字段后挂一个合法版本 ID；目标引擎需要的类型、分区、分桶等配置独立维护，发布时从选定设计版本生成产物。

历史物理 `REVISING` 记录是真实草稿，使用 `LEGACY_DRAFT` 来源语义展示，不改成已发布。历史 `PUBLISHED` 使用 `LEGACY_PUBLISHED`。新发布产物使用 `UNIFIED`，必须记录精确设计版本。已发布设计和产物业务内容不可变；部署绑定的设计归属不可改挂，更换设计须创建新绑定。旧物理头的 `source_logic_version_id` 只表示最初生成依据，不能用于猜测全部历史版本的来源；无法证明的 `design_version_id` 保持空值。

### 数据迁移规则

1. 已有逻辑模型保持原 ID 和历史版本。已有物理关联必须同租户且指向有效对象，不按名称或表名自动合并。
2. 无逻辑关联的物理模型，从逻辑主键序列分配新 ID，记录物理 ID 到新设计 ID 的一对一映射。两个旧序列可能有相同数字，禁止直接复用物理 ID 作为新逻辑 ID。
3. 独立物理模型的最新字段与类型配置复制到新的初始设计草稿，保留字段 UID、来源属性 UID、标准 ID、精度和单位。新草稿不伪造发布人、发布时间或已部署状态。旧物理历史完整留存。
4. 已关联逻辑但仍有独立物理草稿、字段、标准绑定、归属或说明差异时，记录待审查证据。设计和物理两边的数据不得静默相互覆盖；确认前阻止新发布。确认保留历史差异不等于认定两个版本相同。
5. 未知数据库类型、缺失字段身份、无法确定的历史版本来源保留真实状态。后续模型编辑通过已验证的 DB Switch 类型契约处理，不在迁移脚本中猜测类型转换。
6. 0123/0124 阶段按旧授权体系完整保存并核对两端 ACL，不以审查自动授予权限。0126 按明确产品决策退役对象协作权限，切换到角色操作权限与租户隔离；所有原始 ACL 证据保留可追溯。
7. 活动审批、运行或未知部署、仍在登记投递的结果及运行检查在切换前完成对账或正常撤回。不能通过 SQL 把 UNKNOWN 改成失败，不能关闭审批冻结触发器绕过限制。
8. 正式环境从 0123 开始持续停写直至 0126 完成。0123 重放不会刷新已有备份；任何旧页面、任务或直接 SQL 写入导致内容或 ACL 漂移时，0124 拒绝清理。不得覆盖账本强行继续；中止窗口并恢复窗口前备份，修复后重新演练。前期准备及审查演练仅在数据库副本进行。

### 删除范围

清理脚本兼容删除旧结构可能残留的 `theme_id`，并删除物理主表中的重复业务头：`name`、`code`、`description`、`model_style`、`warehouse_layer`、`layer_id`、`subject_domain_id`、`business_process_id`、`data_domain_id`、`table_type`、`classification_status`。删除前逐对象保留原始 JSON 与迁移证据。

保留物理 `id/logic_model_id/source_logic_version_id`、`database_id/db_type/datasource_name/table_name/table_english_name/doris_ext/enabled`、`deploy_status/deployed_version_id/deploy_time` 以及租户、审计、删除标识。`latest_version/status` 暂时保留以正确读取旧物理版本，其语义不再作为统一模型的设计状态。

保留概念表、旧版本表、部署日志、实库基线及落标事实。0126 完整归档后删除协作、审批、报告、通知分发、收件箱和回执七表，以及三个退役按钮对应的角色/套餐关联；其余角色权限保持。清理不得使用 `CASCADE`。规划归属及分层变更触发器中对旧物理业务列的引用必须同时更新，避免删列后直到运行时才报错。

## 状态与发布变更

设计草稿修改后仍保持数据库原有部署状态。发布设计仅固定一个不可变版本；部署目标只接受已固定的设计版本和对应产物。发布向导将这些步骤组合展示，但每一步的失败与重试独立可见。

| 结果 | 页面表达 | 下一步 |
| --- | --- | --- |
| 保存草稿成功 | 设计已修改，目标仍为上次部署版本 | 继续编辑或发布 |
| 设计固定成功，未执行 DDL | 设计已发布，数据库待更新 | 预览并执行目标部署 |
| 外部执行明确失败 | 设计版本保留，部署失败 | 查看失败步骤与实库核验结果 |
| 超时且结果不能确定 | 部署结果待核验 | 使用同一意图核验；不得换请求键盲目重试 |
| DDL 成功，治理登记失败 | 数据库已更新，登记待重试 | 重试原事件，不重建表 |
| 目标结构被库外修改 | 发现结构差异 | 重新生成计划，确认接纳或修正方式 |

DDL 计划包含选定设计版本、目标配置修订、目标结构观测及计划摘要。执行时重新核验，草稿变化、目标配置变化或实库漂移导致计划失效。沿用已有持久部署意图、请求幂等键、租约和补偿核验机制；平台本地事务不承诺回滚外部数据库。

当前新部署通过 DB Switch 执行已验证的产品与操作，开放范围为 PostgreSQL 的建表、增加字段和结构核验。所有新部署动作都检查这一范围，包括不执行 DDL 的 `VERIFY_ONLY`；其他引擎即使列名与类型看似一致，也不能据此生成可执行计划或确认新部署成功。历史部署记录的 `reconcile` 与登记重试继续按原冻结目标和证据工作，不重跑 DDL，也不成为新部署绕过能力检查的入口。

部署计划读取目标的 `deployedVersionId`，以它指向的上次成功部署产物固定字段身份和列名，再与待部署产物比较。同一 `fieldUid` 改名会被识别为改名，已管理 UID 消失会被识别为删除；两者当前均拒绝执行，不能把改名误当成新增空列。存在成功部署证据却缺失产物编号、产物缺失或归属不符、冻结目标不匹配、无法解码或字段证据不完整时，计划不可执行；执行入口同样复核。历史字段缺 UID 时仅能保留其原列名，不猜测改名映射或改写旧快照补证据。

比较范围是上次成功产物实际管理的字段。实库中由其他工具添加、从未由该产物管理的额外列会保留，不被误判为本模型删除列。首次接管没有成功部署历史时同样保留额外列；共同字段的不兼容变化及其他结构漂移仍按原检查拒绝。删除列、重命名、缩短类型等变更需在独立变更流程中处理，当前不提供默认删除重建。退回设计版本不等于数据库自动回滚；重新部署旧版仍受上述字段身份与结构检查约束。

## 权限与跨模块兼容

保留现有 `modeling:model:save/delete/publish/deploy/deploy-reconcile/check/check-config` 操作权限；删除 workspace:approval、collaboration、inbox 三项。统一菜单不会把发布权限提升为数据库部署权限。旧 `generate-physical` 兼容入口也同时校验保存与发布权限。Controller、列表、详情、ER、导出、检查和写操作统一使用角色权限与租户隔离，租户内可见与可写；隐藏菜单不是后端鉴权。

LOGIC 与 PHYSICAL 继续作为历史模型和部署身份编码，前台不要求用户理解。0126 后不再使用协作 Guard、部门 ACL 或所有者策略。旧 ACL 保存在迁移证据，不被复制为新角色授权。

治理的 `MODEL_FIELD` 当前使用 `urn:datahub:model-field:{tenantId}:{physicalModelId}:{fieldUid}`。`ModelFieldApi` 必须保留该身份，新设计 ID 通过独立字段或新契约提供。不能直接把返回编号换成逻辑 ID，导致既有标准映射被置为 STALE 或丢失确认历史。

旧 BPM 实例在切换前由原流程正式结束并对账。0126 原样归档建模审批行后删除建模审批业务表，不修改 BPM 自身记录、不重算旧摘要，也不把新草稿伪装为历史获批设计。

部署向治理发送的 eventId、taskId、correlationId 和冻结载荷继续使用原部署及物理身份。治理登记失败时重试原事件。数据源引用检查继续覆盖历史发布产物和未决部署，即使旧入口已隐藏也不能将数据源误判为无引用。

数据研发任务、数据服务和资产通过各自 API 暴露关联与影响信息；禁止 modeling 直接更新这些模块业务表。标准与质量由 governance 负责，研发任务与调度由 dataforge 负责，数据服务由 supply 负责。

## 实施顺序和验收

先在数据库副本完成准备、映射和清理演练，再实施统一后端、兼容查询、租户与角色权限及前端页面，并在副本上完成全链验收。正式切换时，新版制品已准备好；停止旧实例、部署与检测消费者、审批写入等全部建模写入来源，备份后在同一持续停写窗口执行 0123、逐项审查、0124、0125、0126，然后启动新版并冒烟验证。新应用若不兼容清理前结构，应在 0126 后启动，不能先启动让它写入准备中的库。

| 验收场景 | 必须满足的结果 |
| --- | --- |
| 从零设计维度、明细、汇总表 | 无概念模型或手工逻辑转物理前置；保留类型必要信息 |
| 表单和 ER 往返 | 修改同一字段或关系后另一视图一致，未保存状态明确 |
| 字段改名、删除、复合关联 | UID 稳定；删除有引用提示；历史关系可回看 |
| 并发与租户切换 | revision 冲突不覆盖；旧租户异步响应不回写 |
| 设计发布后部署失败 | 设计版本保留，目标仍显示实际状态 |
| 预览后实库漂移 | 旧 planHash 不可继续执行，要求重新计划 |
| 仅修改 grain | 请求摘要和目标摘要均变化，旧标准门禁凭证不能复用 |
| 非 PostgreSQL 新部署或 VERIFY_ONLY | 返回不可执行计划或明确拒绝，不能按列一致确认成功 |
| 同 UID 改名或删除已管理字段 | 通过 deployedVersionId 冻结证据识别并拒绝，不生成替代新增列 |
| 旧部署产物证据缺失 | 拒绝新部署并提示核对证据，不猜测历史字段身份 |
| 实库存在本模型未管理的额外列 | 保留额外列，不误作删除；共同字段仍接受兼容性核验 |
| 外部执行超时 | 结果保持未知并可对账，不重复副作用 |
| DDL 成功登记失败 | 可重试登记，不重复建表 |
| 独立物理模型迁移 | 新逻辑 ID 不冲突，原版本、草稿、UID、ACL、部署历史全部可追溯 |
| 已有关联但存在差异 | 审查证据完整，未确认时不能新发布，不覆盖一方字段 |
| 旧治理标准映射 | 原物理 URN、确认状态和历史保持可解析 |
| 旧审批、报告与收件箱入口 | API 与页面动作均已退役；原行可由迁移证据追溯，无伪造新历史 |
| 菜单切换 | 现存操作不自动补授新权限，三项退役按钮精确清理；未获得角色查询权者不可访问 |
| 表数据加工 | 汇总口径与实际 SQL 或任务一致；质量检查针对真实数据执行 |

建议用“测站维度—时段降雨明细—测站日降雨汇总”贯穿验收。明确业务日边界、单位、去重和缺测处理；缺测不自动作为零值。这个场景同时验证建模定义、部署、数据研发和质量结果，而不要求先建设完整指标中心。

本轮代码改造必须运行受影响 modeling 模块测试、JSON 契约与真实目标数据库测试；指定测试跨 reactor 使用 `-Dsurefire.failIfNoSpecifiedTests=false`。前端运行边界、typecheck、目标 lint、相关 Vitest，发布前运行 `pnpm run quality:antdv-next`。本次 SQL 验证记录与执行顺序见配套迁移说明。
