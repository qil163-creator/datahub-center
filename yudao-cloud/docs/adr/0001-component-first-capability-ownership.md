# ADR-0001：组件优先与能力归属

- 状态：Accepted
- 日期：2026-09-12

## Context

DataHub 多个业务模块都可能需要数据库、缓存、任务、消息、文件、质量规则等技术能力。如果每个模块各自实现，会产生重复代码、行为分叉和难以统一验证的问题；如果把领域策略全部下沉 Framework，又会反向污染公共组件。

## Decision

1. 业务模块拥有领域规则、权限判断、状态机和流程编排。
2. 跨领域复用、与业务模型解耦且能形成稳定契约的技术机制，进入职责相符的 `yudao-framework` starter。
3. 新增通用技术类前必须检索当前启用组件、公共 API/SPI、生产调用方和测试，并在交付说明记录“直接复用、扩展组件或留在业务”的结论。
4. 组件缺少职责内能力时，先补公共契约、实现和组件测试，再由业务通过薄适配层调用。
5. Framework 不得依赖 `yudao-module-*`，公共模型不得出现业务 VO/DO、权限码、审批状态或模块枚举。

## Consequences

- 业务代码更薄，技术机制只有一个权威实现。
- 组件变更需要承担兼容性、自动配置、依赖成本和直接消费者验证。
- 不为假想复用提前抽象，也不因为只有一个当前调用方就把明显通用的基础能力长期留在业务模块。

## Exceptions

一次性、尚不能稳定抽象或强依赖当前领域状态的行为可保留在业务模块；必须说明为什么不适合进入现有组件。

## Verification

- 检查根 POM 中组件是否启用。
- 检查 Framework 是否引入业务模块依赖或业务类型。
- 运行组件聚焦测试、最小上下文测试和受影响直接消费者测试。
- PR 中记录检索范围和归属结论。
